# Termo — LCD 2004, энкодер и температура

Плата: DOIT ESP32 DEVKIT V1 (ESP32-WROOM-32, 4 МБ Flash).
Профиль PlatformIO: `esp32doit-devkit-v1`. Номера GPIO в схеме — обозначения
сигналов на плате, а не порядковые номера контактов разъёма.
Среда: PlatformIO, Arduino. Дисплей: HD44780-совместимый LCD 20×4
с типовым I²C-переходником PCF8574/PCF8574A или MCP23008.
Маркировка переходника пока не проверена.

## Подключение

Для типового LCD с питанием 5 В используйте двунаправленный преобразователь
уровней I²C 3,3 ↔ 5 В (например, модуль на BSS138 с подтяжками).
На переходнике LCD линии SDA/SCL обычно подтянуты к его питанию:
напрямую подавать 5 В на GPIO ESP32 нельзя.

| Сигнал | Подключение |
| --- | --- |
| ESP32 GPIO21 | LV1 преобразователя → HV1 → LCD SDA |
| ESP32 GPIO22 | LV2 преобразователя → HV2 → LCD SCL |
| ESP32 3V3 | LV преобразователя |
| ESP32 5V при питании платы от USB | HV преобразователя и LCD VCC |
| ESP32 GND | LCD GND и GND преобразователя |

На этом этапе плата питается только от USB.

| Энкодер с кнопкой | ESP32 |
| --- | --- |
| CLK | GPIO32 |
| DT | GPIO33 |
| SW | GPIO25 |
| + / VCC | 3V3 |
| GND | GND |

Для голого механического энкодера общий контакт вращения и второй контакт
кнопки подключите к GND. Входы используют `INPUT_PULLUP`.

| Трёхпроводной DS1820 / DS18S20 / DS18B20 | ESP32 |
| --- | --- |
| VDD | 3V3 |
| DQ / DATA | GPIO27 |
| GND | GND |

Между DATA и 3V3 нужен резистор 4,7 кОм. Паразитное питание не используется.
Назначение проводов проверьте по конкретному датчику: цвета кабелей не стандартны.
На шине предполагается один датчик. Его семейство определяется автоматически.

## Сборка и проверка

В PlatformIO выполните Build, затем Upload и откройте Serial Monitor
на скорости 115200. В терминале PlatformIO эквивалентные команды:

```text
pio run
pio run --target upload
pio device monitor
```

Ожидаемый экран:

```text
Room:   --.- C
Avg 5m: --.- C
Target: 23.0 C
Pump:   OFF
```

После первого успешного измерения вместо `--.-` появляется реальная температура.
При отсутствии датчика или ошибке чтения снова отображается `--.-`.
Уставка пока тестовая. `Pump` показывает заданное состояние выхода
реле; обратной связи о фактическом вращении насоса нет.
При успешной инициализации Serial выводит `LCD ready.`.
При ошибке выводится `LCD initialization failed:` с кодом драйвера.
Если подсветка есть, но текст не виден, отрегулируйте контраст подстроечником.

## Код

`lib/LcdUi` — начало нашей библиотеки интерфейса: инициализация и главный экран.
Данные передаются через `HomeData`; перерисовываются только изменённые строки,
без очистки всего экрана при обновлении. Адрес и распиновку поддерживаемого
переходника автоматически определяет драйвер
[hd44780](https://github.com/duinoWitchery/hd44780).

## Скользящее среднее и меню

`AverageModule` хранит корректные измерения последних 60 минут в статическом
кольцевом буфере (около 14 КБ RAM). Каждое новое измерение учитывается один раз
по его номеру и времени получения. Среднее — арифметическое по измерениям в
выбранном окне; ошибки не включаются и не заменяются повтором старой температуры.
После старта расчёт идёт по доступной истории, без ожидания полного окна.
При отключении датчика среднее может ещё показывать прежние корректные данные,
пока они находятся в окне. Если данных в окне нет, отображается `--.-`.
История не сохраняется при перезагрузке.

Период — 1–60 минут, шаг 1 минута, по умолчанию 5. При изменении периода
используется уже накопленная история. Размер буфера рассчитан на интервал
измерений не менее 2 секунд; при ускорении датчика его нужно пересмотреть.

Управление:

1. Нажать энкодер на главном экране — открыть `Menu`.
2. Выбрать `Settings`, затем `Avg period` нажатием.
3. Вращением задать минуты; нажатие сохраняет значение и возвращает в `Settings`.
4. Пункт `Back` возвращает на уровень выше, из `Menu` — на главный экран.

Период сохраняется в NVS через `Preferences` (пространство `termo`, ключ
`avg_minutes`) только при подтверждении изменённого значения. После перезагрузки
он восстанавливается; отсутствующее или некорректное значение заменяется на 5.
Ошибка сохранения оставляет редактор открытым с `Save failed. Retry`, действующий
период остаётся прежним. Регулирование насоса не добавлено.

Проверка на плате: задать 1 минуту, вернуться через `Back`, убедиться в строке
`Avg 1m`, перезагрузить плату и проверить сохранение 1 минуты. Проверить пределы
1 и 60, отсутствие повторов при удержании кнопки и появление прочерков при
пустом окне после отключения датчика.

## Энкодер и температура

`EncoderModule` опрашивается каждые 1 мс и использует
[EncButton от AlexGyver](https://github.com/GyverLibs/EncButton) версии 3.7.6.
Обработку каналов и дребезга выполняет библиотека, собственного декодера нет.
Используется `VirtEncButton`: GPIO настраиваются в `begin()`, их значения
передаются в `tick()`. Антидребезг кнопки — 50 мс; событие берётся из `press()`,
поэтому удержание не повторяет нажатие. События читаются и очищаются внутри
`update()`, чтобы не повторяться между вызовами планировщика.
`takeRotation()` забирает накопленное смещение, `takePress()` — флаг нажатия.
События забирает `DisplayModule` для навигации и редактирования периода.
Уставку энкодер пока не меняет. Если направление обратное,
измените `setEncReverse(false)` на `setEncReverse(true)` в `EncoderModule.cpp`.
Сейчас выбран тип `EB_STEP4_LOW` (четыре перехода на щелчок, подтяжка к VCC).
Если получается один шаг на два щелчка, выберите `EB_STEP2` через `setEncType()`.
Опрос программный: при быстром вращении во время обмена с LCD/датчиком возможны
пропуски. Период планировщика не гарантирует вызов строго каждую миллисекунду.

`TemperatureModule` обслуживается каждые 10 мс, запускает измерение примерно
раз в 2 секунды и читает результат через 800 мс. Во время преобразования
остальные модули работают. Сам обмен 1-Wire синхронный и занимает несколько
миллисекунд. CRC проверяет драйвер; ошибки и значения вне диапазона −55…125 °C
превращаются в `NAN`. Датчик ищется заново перед измерением, поэтому после
подключения/замены работа восстанавливается без перезагрузки.
Температура копируется в `HomeData` в основном цикле и обновляется на LCD
в ближайший вызов модуля дисплея. До обнаружения обрыва может оставаться
предыдущее значение, максимум до следующей попытки измерения.

Драйверы: [DallasTemperature](https://github.com/milesburton/Arduino-Temperature-Control-Library)
и [OneWire](https://github.com/PaulStoffregen/OneWire).

## Выход реле насоса

`PumpModule` реализует `IModule`, зарегистрирован с периодом 100 мс.
`update()` намеренно пустой: автоматической логики управления пока нет.
`begin()` устанавливает выключенное состояние; `setOn(bool)` задаёт выход,
`isOn()` возвращает заданное состояние. До `begin()` команды игнорируются.
Сейчас команды включения в программе отсутствуют.

В `src/main.cpp` заданы GPIO26 и `pumpRelayActiveHigh = true`: HIGH включает,
LOW выключает. Для реле с активным LOW установите `false` до подключения.
GPIO26 подключается к IN релейного модуля с входом, совместимым с 3,3 В,
GND — к общей земле. Катушку реле напрямую к GPIO не подключают.
Состояние до запуска прошивки определяется аппаратно: при необходимости
удерживать OFF во время сброса нужна подтяжка IN к неактивному уровню.
Модуль насоса инициализируется первым, до LCD и датчика.

## Планировщик модулей

`lib/Scheduler` — кооперативный планировщик без динамического выделения памяти.
Общий интерфейс `IModule`: `bool begin()` и `void update()`.
Модули вызываются последовательно в порядке регистрации из Arduino `loop()`.
Внутри `update()` нельзя использовать длительные ожидания и `delay()`:
долгий вызов задерживает остальные модули.

В `src/main.cpp` создаётся `Scheduler<5>` на пять модулей. В `setup()` регистрируются
насос (100 мс), энкодер (1 мс), температура (10 мс), среднее (100 мс) и дисплей
(20 мс для реакции меню; на LCD передаются только изменённые строки),
затем `scheduler.begin()` инициализирует модули. `loop()` вызывает `tick()`.
Чтобы добавить модуль, реализуйте `IModule`, создайте объект со временем жизни
не меньше планировщика, увеличьте его ёмкость и вызовите `add()` до `begin()`.

- Периоды и список модулей после запуска неизменны.
- `add()` возвращает `false` при нулевом периоде, повторной регистрации,
  отсутствии свободного места или регистрации после запуска.
- Неуспешный `begin()` модуля отключает его периодические вызовы;
  остальные модули продолжают работать. Повторная инициализация не выполняется.
- Первый `update()` планировщика наступает через заданный период после
  завершения общей инициализации. Дисплей дополнительно рисует экран в своём
  `begin()`, чтобы он появился сразу.
- Следующий вызов наступает не раньше чем через период после завершения
  предыдущего. Пропущенные интервалы не воспроизводятся; это не точный таймер.
- Переполнение `millis()` обрабатывается беззнаковым вычитанием. Между проверками
  времени не должно проходить полного оборота счётчика (около 49,7 суток).

Логику времени можно проверить на ПК с GCC, без платы:

```powershell
g++ -std=c++11 -Wall -Wextra -pedantic -Ilib/Scheduler test/scheduler_test.cpp -o "$env:TEMP\termo_scheduler_test.exe"
& "$env:TEMP\termo_scheduler_test.exe"
g++ -std=c++11 -Wall -Wextra -pedantic -Ilib/TemperatureAverage test/temperature_average_test.cpp -o "$env:TEMP\termo_average_test.exe"
& "$env:TEMP\termo_average_test.exe"
```
